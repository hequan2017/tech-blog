> **About this post**
>
> This post centers on the ops project of "centralized management of server user permissions and auditing of operation behavior logs": it first reviews account and permission management commands such as useradd/usermod/passwd/chage/sudo, then presents a shell script for batch user creation along with the essentials of sudoers configuration (aliases, whitelist, full command paths), and finally implements sudo operation logging (sudo logfile + rsyslog), mentioning scribe/Flume/Logstash/Kibana as optional solutions for centralized log collection.

> **Technical notes**
>
> Status of the components mentioned in this post as of 2026: `passwd --stdin` has been removed in RHEL 8+/Rocky 9; use `chpasswd` instead. rsyslog is still mainstream, but the default logging on most distributions has shifted to systemd-journald. sudo 1.9+ supports `log_subcmds` and the centralized `sudo_logsrvd` logging service. The scribe/storm approach is long obsolete; mainstream log collection is now ELK/EFK (Elasticsearch+Fluent Bit+Kibana) or Loki+Grafana. CentOS 6/7 are both EOL.

## 1. Account and Permission Management Command Cheat Sheet

```shell
useradd  -g primary_group -u UID -c comment -s shell -d home_dir -G extra_groups -M no_home_dir
useradd  -D          # show/change default attributes
userdel  -r username # delete a user together with the home directory
usermod              # modify an existing user
groupadd / groupdel  # add/remove user groups

passwd --stdin       # read the password from stdin (for batch changes; note: removed in RHEL 8+, use chpasswd instead)
chage -l username    # view password expiry attributes
chage -E date username # set the account expiration time

su - username        # switch user and load its environment variables
su - username -c "command" # run a command as that user, then return to the current user

newgrp groupname     # switch the current effective group
id username          # view user UID/GID and group memberships
w / who / last / lastlog / whoami / finger   # logged-in users and historical behavior auditing
```

## 2. Batch User Creation Script

```shell
for user in aaa bbb ccc
do
    useradd $user
    echo "123123" | passwd --stdin $user > /dev/null 2>&1   # set the initial password non-interactively
done
```

> Note: on newer systems, rewrite this as `echo "$user:123123" | chpasswd`.

## 3. Centralized Permission Management with sudo

sudo gives ordinary users root privileges within the authorized scope; the configuration file must be edited through `visudo` (with syntax checking).

Key points for writing sudoers:

- Commands must be written as **absolute paths** (look them up with `which`).
- Alias names must be **UPPERCASE**; use `\` for line continuation when one line is not enough.
- Authorization format: `user host=(run_as) command`; the default identity is root, and `(ALL)` means any identity.
- `%groupname` grants the permission to a user group; `!command` denies that command (whitelist mechanism).
- Follow a **whitelist approach**: allow only the commands that are actually needed, instead of allowing everything and excluding the rest with a blacklist (in the source article, "whitelist wit" is a typo for "whitelist mechanism").

```shell
sudo -l    # list the sudo commands the current user is authorized to run
```

## 4. sudo Operation Log Auditing

Confirm the components are installed:

```shell
rpm -aq | egrep "sudo|rsyslog"
# sudo-1.8.6p3-12.el6.x86_64
# rsyslog-5.8.10-8.el6.x86_64
```

Method 1: let sudo write its own log file (in the source article, "suo command log" is a typo for "sudo command log"):

```shell
echo "Defaults  logfile=/var/log/sudo.log" >> /etc/sudoers
visudo -c          # validate the sudoers syntax
# /etc/sudoers: parsed OK
```

Method 2: collect sudo logs through rsyslog:

```shell
echo "local2.debug   /var/log/sudo.log" >> /etc/rsyslog.conf
/etc/init.d/rsyslog restart      # CentOS 6 syntax; on CentOS 7+ use systemctl restart rsyslog
ll /var/log/sudo.log
# -rw------- 1 root root 0 Mar 27 20:45 /var/log/sudo.log
```

## 5. Centralized Log Collection Solutions

Logs on standalone machines can be synced in real time to a log server with `rsync + inotify`, or forwarded remotely by rsyslog directly. Options for distributed log collection:

- Early solutions: scribe, Flume, Storm (in the source article, "kibanan" is a typo for Kibana) — all of these had been phased out or marginalized by 2026.
- Current mainstream: Logstash/Fluent Bit + Elasticsearch + Kibana (ELK/EFK), or the lightweight Loki + Grafana.

## 6. Project Implementation Methodology (Key Points from the Original)

Reworking permission management is not just about typing commands; it is a complete project whose core idea is **minimization**: minimized software installation, minimized directory/file permissions, minimized user privileges, and minimized privileges for running programs.

Process: raise the issue → write the solution and planning documents → discuss feasibility → consolidate and submit for review → finalize the solution → implement and deploy → summarize and maintain. Also provide proper training and accumulate documentation, managing the entire process in a standardized way.
