> **About this post**
>
> This post demonstrates reverse-proxy load balancing with Nginx: compiling nginx 1.10.0 from source (with the stub_status and ssl modules enabled, then symlinked to /application/nginx), defining an upstream backend in the http block of nginx.conf pointing to two backend servers (with the max_fails/fail_timeout health-check parameters), forwarding requests via proxy_pass in the server block, and verifying the round-robin behavior and the automatic removal of a failed node with a for-loop curl; it closes by comparing four approaches to session persistence: ip_hash, session replication, memcache sharing, and cookies+session.

> **Technical notes**
>
> Nginx configuration varies slightly across major versions; for the current stable releases (1.24+/1.26+), the official documentation is authoritative. Note: version 1.10.0 used here is no longer maintained, but the upstream/proxy_pass syntax in current stable releases remains compatible with this post; ip_hash distributes unevenly across multiple data centers or when clients go through proxies — more general solutions are sticky sessions or centrally shared sessions such as Redis.

## 1. Compile and install nginx

```shell
wget http://nginx.org/download/nginx-1.10.0.tar.gz
tar xf nginx-1.10.0.tar.gz
cd nginx-1.10.0

./configure --user=nginx --group=nginx \
    --prefix=/application/nginx.1.10.0 \
    --with-http_stub_status_module \
    --with-http_ssl_module

make
make install

ln -s /application/nginx.1.10.0/ /application/nginx
useradd nginx -s /sbin/nologin -M

/application/nginx/sbin/nginx -t     # check the syntax
/application/nginx/sbin/nginx        # start nginx

egrep -v "#|^$" nginx.conf.default > nginx.conf   # strip comments to generate a minimal config
```

## 2. Configure load balancing

```nginx
# vim nginx.conf
http {
    upstream backend {
        ip_hash;    # after login, always lands on the same server
        server 192.168.10.11:80  max_fails=3 fail_timeout=30s;
        server 192.168.10.16:80  max_fails=3 fail_timeout=30s;
    }

    server {
        listen       80;
        server_name  ;
        index        index.html index.htm;

        location / {
            proxy_pass http://backend;
        }
    }
}
```

At this point, opening 192.168.10.10 hits the backends in a **round robin (rr)** fashion, alternating between 11 and 16.

## 3. Testing

```shell
for n in `seq 100`; do curl 192.168.10.10; sleep 2; done
```

After shutting down one of the servers, access still works normally without interruption; once that server recovers, it automatically rejoins and starts serving requests again.

## 4. A few approaches to session persistence

When every server writes login information locally, it disrupts user logins — users get bounced back and forth between login states:

- **Session persistence at the lb layer** (fine for low traffic): add `ip_hash;` so a user always stays on the same server after login
- **Session replication at the application layer**
- **Shared storage**, such as memcache
- **Cookies combined with sessions**, caching user-level session data locally on the user's side
