## 1. Iterator

An iterator is a way of accessing the elements of a collection. An iterator object starts from the first element of the collection and walks through until every element has been visited. An iterator can only move forward, never backward — but that hardly matters, because people rarely step backward in the middle of iterating. Another big advantage of iterators is that they do not require all elements of the whole iteration to be prepared in advance. An iterator computes an element only when the iteration reaches it; before or after that, the element may not exist or may already have been destroyed. This makes iterators especially well suited to traversing huge or even infinite collections, such as a file several gigabytes in size.

Characteristics:

1. Visitors do not need to care about the iterator's internal structure; they simply keep fetching the next item via the **next()** method
2. No random access to any value in the collection; items can only be visited from start to end in order
3. Cannot move backward once partway through
4. Convenient for looping over large data collections and saves memory

```python
names = iter(['alex', 'jack', 'list'])

print(names)
print(names.__next__())   ## next() in 2.7
print(names.__next__())
print(names.__next__())
```

Output:

```text
<list_iterator object at 0x000001850C3AA748>
alex
jack
list
```

## 2. Generator

Definition: a function that returns an iterator when called is called a generator; if a function contains the yield syntax, that function becomes a generator.

```python
#!/usr/bin/env python
# -*- coding: utf-8 -*-

def cash_out(amount):
    while amount > 0:
        amount -= 1
        yield 1
        print("擦，又来取钱了。。。败家子！")

ATM = cash_out(5)

print(type(ATM))
print("取到钱 %s 万" % ATM.__next__())
print("花掉花掉!")
print("取到钱 %s 万" % ATM.__next__())
print("取到钱 %s 万" % ATM.__next__())
print("花掉花掉!")
print("取到钱 %s 万" % ATM.__next__())
print("取到钱 %s 万" % ATM.__next__())
# print("取到钱 %s 万" % ATM.__next__())   # by now the money is gone; another call would raise an error
# print("取到钱 %s 万" % ATM.__next__())
```

### yield for async: producer-consumer (eating baozi)

The original omitted `import time`; it has been added back:

```python
import time

def consumer(name):
    print("%s 准备吃包子啦!" % name)
    while True:
        baozi = yield
        print("包子[%s]来了,被[%s]吃了!" % (baozi, name))

def producer(name):
    c = consumer('A')
    c2 = consumer('B')
    c.__next__()
    c2.__next__()
    print("老子开始准备做包子啦!")
    for i in range(10):
        time.sleep(1)
        print("做了2个包子!")
        c.send(i)
        c2.send(i)

producer("alex")
```

## 3. The relationship between Iterable and Iterator

- Any object that can be used in a for loop is an Iterable;
- Any object that works with the next() function is an Iterator; they represent a lazily computed sequence;
- **Collection data types such as `list`, `dict`, and `str` are `Iterable` but not `Iterator`**, though you can obtain an `Iterator` from them via the `iter()` function.

Python's `for` loop is essentially implemented by repeatedly calling the `next()` function, for example:

```python
for x in [1, 2, 3, 4, 5]:
    pass
```

is in fact fully equivalent to (this passage was garbled in the original layout; reformatted here):

```python
# First, obtain an Iterator object:
it = iter([1, 2, 3, 4, 5])
# Loop:
while True:
    try:
        # Get the next value:
        x = next(it)
    except StopIteration:
        # Exit the loop when StopIteration is raised
        break
```

An Iterator can even represent an infinitely large stream of data.

- Iterable: an object that can be iterated over
- Iterator: an iterator

## 4. Decorator

Closed: implemented feature code must not be modified; open: open for extension. The rule is that already-implemented feature code must not be modified, but it can be extended.

```python
def w1(func):
    def inner():
        # validation 1
        # validation 2
        # validation 3
        return func()
    return inner

@w1
def f1():
    print 'f1'      # Python 2 syntax

@w1
def f2():
    print 'f2'

@w1
def f3():
    print 'f3'

@w1
def f4():
    print 'f4'
```

Usage: put `@decorator` above the function.

Summary: an iterator is a way of accessing collection elements (`iter()`, `next()`); a function that uses yield is called a generator.

### functools.wraps preserves function metadata

```python
#!/usr/bin/env python
# -*- coding: utf-8 -*-

import functools

def logging(func):
    @functools.wraps(func)
    def decorator():
        print("%s called" % func.__name__)
        result = func()
        print("%s end" % func.__name__)
        return result
    return decorator

# apply the decorator
@logging
def test01():
    return 1

# test cases
print(test01())
print(test01.__name__)
```

The version with arguments:

```python
#!/usr/bin/env python
# -*- coding: UTF-8 -*-

import functools

def logging(func):
    @functools.wraps(func)
    def decorator(*args, **kwargs):
        print("%s called" % func.__name__)
        result = func(*args, **kwargs)
        print("%s end" % func.__name__)
        return result
    return decorator

@logging
def test01(a, b):
    print("in function test01,a=%s,b=%s" % (a, b))
    return 1

@logging
def test02(a, b, c=1):
    print("in function test02,a=%s,b=%s,c=%s" % (a, b, c))
    return 1

print(test01(1, 2))
print(test02(1, 2, c=3))
```

## 5. Directory organization

As for how to organize a good Python project directory structure, some commonly agreed-upon layouts already exist. On [this question](http://stackoverflow.com/questions/193161/what-is-the-best-project-structure-for-a-python-application) on Stackoverflow, you can see people discussing Python directory structure.

What is described there is already very good, and I have no intention of reinventing the wheel by enumerating all the different approaches; here I will just share my own understanding and experience.

Suppose your project is named foo — the most convenient and quick directory structure I recommend is simply this:

```text
|-- bin/
|   |-- foo
|
|-- foo/
|   |-- tests/
|   |   |-- __init__.py
|   |   |-- test_main.py
|   |
|   |-- __init__.py
|   |-- main.py
|
|-- docs/
|   |-- conf.py
|   |-- abc.rst
|
|-- setup.py
|-- requirements.txt
|-- README
```

A brief explanation:

1. `bin/`: holds some of the project's executable files; naming it `script/` or something similar works too.
2. `foo/`: holds all of the project's source code. (1) All modules and packages of the source code should be placed in this directory, not at the top level; (2) its `tests/` subdirectory holds the unit test code; (3) the program entry point is best named `main.py`.
3. `docs/`: holds some documentation.
4. `setup.py`: the script for installation, deployment, and packaging.
5. `requirements.txt`: the list of external Python packages the software depends on.
6. `README`: the project description file.

Beyond that, some schemes include more content, such as `LICENSE.txt` and `ChangeLog.txt` files; I have not listed them here because those things are mainly needed when a project is open-sourced. If you want to write an open-source application and are wondering how to organize the directory, you can refer to [this article](http://www.jeffknupp.com/blog/2013/08/16/open-sourcing-a-python-project-the-right-way/).

### About the contents of the README

**I think this is a file every project should have**; its purpose is to briefly describe the project's information so readers can quickly understand it.

It needs to state the following:

1. The software's positioning and its basic functionality.
2. How to run the code: installing the environment, startup commands, and so on.
3. Brief usage instructions.
4. An explanation of the code directory structure — in more detail, the basic principles of the software.
5. Frequently asked questions.

I think a `README` that covers these points is a good one. In the early stages of development, since the above may be unclear or may change during the process, you do not have to fill everything in at the very beginning. But by the time the project is finished, such a document needs to be written.

For reference, look at the [Readme](https://github.com/antirez/redis#what-is-redis) in the Redis source, which describes Redis's features and source structure concisely yet clearly.

### About requirements.txt and setup.py

**setup.py**

Generally speaking, `setup.py` is used to manage the packaging, installation, and deployment of the code. The industry-standard way is to manage these things with Python's popular packaging tool [setuptools](https://pythonhosted.org/setuptools/setuptools.html#developer-s-guide). This approach is widely used in open-source projects. But the core idea here is not to use a standardized tool to solve these problems; rather, **a project must have an installation and deployment tool**, one that can quickly and conveniently set up the environment, deploy the code, and get the program running on a brand-new machine.

I have been burned by this myself. When I first started writing Python projects, environment setup, code deployment, and running the program were all done manually, and I ran into the following problems:

1. When installing the environment I often forgot that yet another new Python package had been added recently, and the program would error out as soon as it ran in production.
2. Python package version dependencies: sometimes the program used one version of a Python package while the official one had already moved on to the latest; installing by hand could easily install the wrong version.
3. If there are many dependent packages, installing them one by one is a very time-consuming task.
4. When newcomers start on a project, getting the program running is a real hassle, because they often forget how to install the various dependencies.

`setup.py` can automate all of these things, improving efficiency and reducing the chance of error. "Automate anything complex; anything that can be automated must be automated." is a very good habit.

The [documentation](https://pythonhosted.org/setuptools/setuptools.html#developer-s-guide) for setuptools is quite large, and if you are new to it you may not know where to start. The way to learn a technology is to see how others use it — for example, look at how Flask, a Python web framework, writes its [setup.py](https://github.com/mitsuhiko/flask/blob/master/setup.py).

Of course, a simpler alternative — writing your own install script (`deploy.sh`) in place of `setup.py` — is perfectly acceptable too.

**requirements.txt**

The purpose of this file is:

1. To make it easy for developers to maintain the software's package dependencies. Add newly introduced packages to this list as you go, to avoid missing packages when `setup.py` installs dependencies.
2. To make it easy for readers to see exactly which Python packages the project uses.

The file format is one dependency description per line, usually something like `flask>=0.10`; the requirement is that the format be recognizable by pip, so you can simply install all Python package dependencies with `pip install -r requirements.txt`. Format details: [see here](https://pip.readthedocs.org/en/1.1/requirements.html).

### About how to use configuration files

Note that in the directory structure above, `conf.py` is not placed under the source directory but under the `docs/` directory.

The practice in many projects is:

1. The configuration is written in one or more Python files, such as conf.py here.
2. Whichever module in the project needs this configuration simply uses `import conf` in the code.

I don't much agree with this approach:

1. It makes unit testing difficult (because modules internally depend on external configuration).
2. Moreover, the configuration file serves as the user's interface for controlling the program, and its path should be freely specifiable by the user.
3. Component reusability suffers badly, because this hard-coded pattern running through all modules makes most of them depend on the `conf.py` file.

So the better way to use configuration, in my view, is:

1. Each module's configuration is flexibly configurable and unaffected by external configuration files.
2. The program's configuration is also flexibly controllable.

Evidence supporting this idea: anyone who has used nginx and mysql knows that these programs let users freely specify their own configuration.

So you should not `import conf` directly in code to use a configuration file. The `conf.py` in the directory structure above is a configuration example, not a configuration file hard-wired into the program for direct reference. You can have the program read its configuration by passing a configuration path as a startup argument to `main.py`. Of course, you can rename this `conf.py` to a similar name like `settings.py`, or write the configuration in another format altogether, such as `settings.yaml`.

## 6. Appendix: recursion, binary search, and matrix transposition

Recursion — calling itself:

```python
def func(arg1, arg2, stop):
    if arg1 == 0:
        print(arg1, arg2)
    arg3 = arg1 + arg2
    print(arg3)
    if arg3 < stop:
        func(arg2, arg3, stop)

func(0, 1, 30)
```

Binary search (`ringt` in the original was a typo for `right`; fixed):

```python
#!/usr/bin/env python
# -*- coding: utf-8 -*-

## binary search
def binary_search(data_source, find_n):
    mid = int(len(data_source) / 2)
    if len(data_source) >= 1:
        if data_source[mid] > find_n:
            print("data in left of {}".format(data_source[mid]))
            binary_search(data_source[:mid], find_n)
        elif data_source[mid] < find_n:
            print("data in right of {}".format(data_source[mid]))
            binary_search(data_source[mid:], find_n)
        else:
            print("found find_s,", find_n)
    else:
        print("这些找不到")

if __name__ == '__main__':
    data = list(range(1, 6))
    # print(data)
    binary_search(data, 2)
```

Matrix transposition:

```python
a = [[col for col in range(4)] for row in range(4)]

for r_index, row in enumerate(a):
    for c_index in range(r_index, len(row)):
        tmp = a[c_index][r_index]
        a[c_index][r_index] = row[c_index]
        a[r_index][c_index] = tmp

for r in a:
    print(r)
```
