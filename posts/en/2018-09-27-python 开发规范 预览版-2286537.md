> **About this post**
>
> A custom Python development style guide (preview), compiled mainly with reference to PEP8 and the JumpServer development guidelines. It covers code linting tools, layout conventions such as imports, exceptions, indentation, line length, blank lines and whitespace, string formatting, comparison and naming conventions, function arguments, Docstring and comment practices, and module header declarations.

> **Technical notes**
>
> The main body of the guidelines still applies today. One addition: mainstream community tooling has since expanded from pylint to combinations of black/isort/flake8/ruff, and formatting can now be fully automated. Python 3 defaults to UTF-8, so the `# -*- coding: utf-8 -*-` declaration at the top of source files can be omitted in new projects.

### Python Development Guidelines (Preview)

This document mainly draws on pep8 and the jumpserver development guidelines, with adjustments based on actual practice. Comments and suggestions for improvement are welcome.

#### Code Linting Tools

- pylint
- pycharm --> code --> Reformat Code  formats the current file's code style
- pycharm --> right-click the project --> Inspect Code  checks the current project against the pep8 style

#### Basic Code Layout

##### Imports

```python
import x
from x import y
from x import y as z

# Do not use import x, y
```

##### Exceptions

Use as

```python
try:
    raise Error
except Error as error:
    pass
```

##### Indentation

1. Python strictly uses 4-space indentation; all Python code must follow this rule.
2. Leave one space after the `,` character.

##### Maximum Line Length

Limit the maximum line length to 120 characters.

##### Indentation of Long Statements

When writing long statements, you can use the line continuation character `\`. In that case, the next line should align with the last `.` period or `=` of the previous line, or be indented by 4 spaces.

```python
this_is_a_very_long(function_call, 'with many parameters') \
    .that_returns_an_object_with_an_attribute

MyModel.query.filter(MyModel.scalar > 120) \
             .order_by(MyModel.name.desc()) \
             .limit(10)
```

If you wrap a long statement with parentheses `()` or braces `{}`, the next line should align with the opening parenthesis or brace:

```python
this_is_a_very_long(function_call, 'with many parameters',
                    23, 42, 'and even more')
```

For lists or tuples with many elements, break the line right after the first `[` or `(`:

```python
items = [
    'this is the first', 'set of items', 'with more items',
    'to come in this line', 'like this'
]
```

##### Blank Lines

Separate top-level functions and classes by two blank lines; use a single blank line everywhere else. Do not use excessive blank lines in code to separate different logical sections.

```python
def hello(name):
    print('Hello %s!' % name)


class MyClass(object):
    """This is a simple docstring."""

    def __init__(self, name):
        self.name = name

    def get_annoying_name(self):
        return self.name.upper() + '!!!!111'
```

##### Whitespace Rules

No whitespace between a unary operator and its operand (e.g. `-`, `~`, etc.), even when the unary operator is inside parentheses. Use whitespace between binary operators and their operands.

```python
exp = -1.05
value = (item_value / item_count) * offset / exp
value = my_list[index]
value = my_dict['key']
```

#### String Formatting

Use `f'{name}{value}'`

##### Comparisons

- For comparisons between arbitrary types, use `isinstance(L, list)` and `not isinstance(L, list)`.
- When comparing against singletons, use is and is not.
- Never compare directly against True or False (for example, do not write `foo == False`; write `if not foo` instead).
- For negated membership tests, use `foo not in bar` instead of `not foo in bar`.

##### Naming Conventions

- Class names: CamelCase.
- Variable names: lowercase_with_underscores.
- Method and function names: lowercase_with_underscores.
- Constants: UPPERCASE_WITH_UNDERSCORES.
- Precompiled regular expressions: name_re.
- Protected elements are prefixed with a single underscore. A double underscore prefix is used only when defining mixin classes.
- If a keyword is used as a class name, append a trailing underscore. Shadowing built-in names is allowed; do not append an underscore to a variable name to distinguish it. If a function needs to access a built-in with the same name, rebind the built-in to a different name.
- Names should be meaningful; do not use pinyin or meaningless single letters (loop counters are the exception, e.g. `for i in`).
- Be cautious with abbreviations in names; stick to widely accepted ones.
- Avoid global variables as much as possible; use class variables instead.

##### Function and Method Arguments:

- Class methods: cls is the first argument.
- Instance methods: self is the first argument.
- When using lambdas in property functions, the first argument of the lambda may be x, e.g.: `display_name = property(lambda x: x.real_name or x.username)`.
- Do not name a parameter simply id; use something else instead, e.g. asset_id.

##### Docstrings (documentation comments for methods and classes)

All docstrings are written in reStructuredText format so that Sphinx can process them conveniently. The layout of a docstring varies with its number of lines. For a single line, the closing triple quotes stay on the same line as the opening triple quotes. For multiple lines, the text of the docstring starts right after the opening triple quotes, and the closing triple quotes go on their own line. (Write docstrings in English whenever possible; otherwise write them in elegant Chinese.)

```python
def foo():
    """This is a simple docstring."""

def bar():
    """This is a longer docstring with so much information in there
    that it spans three lines.  In this case, the closing triple quote
    is on its own line.
    """
```

A docstring should consist of a brief summary (one line if possible) and a detailed description. If necessary, separate the summary from the detailed description with a blank line.

##### Comments (for classes and functions)

```python
def AvailableZones(self, instance_charge_type, region_id):
    """
    Purpose: availability zones
    :param instance_charge_type: billing method
    :param region_id:    region
    :return:  ['cn-huhehaote-a', 'cn-huhehaote-b']
    """
```

##### Module Header

The header of a module file contains the utf-8 encoding declaration (recommended if the module uses non-ASCII characters) and the standard docstring.

```python
#!/usr/bin/env python3.6
# -*- coding: utf-8 -*-
```
