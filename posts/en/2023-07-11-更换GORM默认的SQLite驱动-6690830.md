> **About this post**
>
> In the official GORM Issues, the author came across reports about the SQLite driver depending on CGO. Following the trail, he found `glebarez/sqlite`, a pure Go implementation with no CGO dependency. Swapping it in for the official default driver makes it possible to build a static binary that does not rely on dynamic libraries; the cost of this replacement is recorded at the end of the post.

> **Technical notes**
>
> `gorm.io/driver/sqlite` is built on top of `mattn/go-sqlite3`, which relies on CGO and requires a C toolchain for the target platform when cross-compiling; `glebarez/sqlite` is based on `modernc.org/sqlite` (a pure Go port of SQLite) and has no CGO dependency, at the cost of slightly lower performance and a larger binary — consistent with the "cost" mentioned in the post.

---

In the official GORM Issues, I noticed that someone else had reported the same problem. Following the trail, I found the library `github.com/glebarez/sqlite`, which is implemented in pure Go and does not depend on CGO. Here is the address: [https://github.com/glebarez/sqlite](https://github.com/glebarez/sqlite)

So I replaced the official driver:

```go
import (
    "gorm.io/driver/sqlite"
    "gorm.io/gorm"
)
```

with:

```go
import (
    "github.com/glebarez/sqlite"
    "gorm.io/gorm"
)
```

This way, you can compile a static binary without depending on CGO, which solves the problem of relying on dynamic libraries across platforms.

#### The Cost

- `glebarez/sqlite` does not perform as well as the official driver, but trading a small amount of performance for convenience is worthwhile in my opinion. If you have no cross-platform needs, just stick with the official default driver.
- The size of the statically compiled, packaged binary increases noticeably.
